# 04 — Canonical Data Model

## 1. Design goals

The schema must support different facility types without turning `facilities` into a huge table of nullable columns. It must also preserve the original source representation, track attribute-level provenance, and record history.

### Core rules

- A canonical facility ID is stable and generated by PhilFacilities; it is not derived from the facility name.
- Every agency-specific identifier is stored separately and remains unique within its source system.
- One canonical facility may link to several source records.
- One source record must not be merged into a canonical entity solely because names look similar.
- Domain-specific observations (enrollment, bed capacity, accreditation) are dated and source-linked.
- Null means unknown/not supplied. Do not coerce null to zero, false, inactive, or not applicable.
- Geography uses string codes to preserve leading zeros and release context.

## 2. Logical schema

Suggested PostgreSQL schemas:

- `core`: canonical facilities and common attributes.
- `geo`: PSGC geographic entities, releases, and crosswalks.
- `source`: agencies, datasets, releases, raw records, and provenance.
- `school`: school profiles and dated education observations.
- `health`: health facility profiles, licenses, and accreditations.
- `quality`: validation issues, reviews, and quality metrics.
- `history`: canonical change events and temporal versions.

## 3. Core tables

### `core.facilities`

| Column | Type | Notes |
|---|---|---|
| `id` | UUID | Stable canonical identifier |
| `slug` | text | Human-readable optional slug; not identity key |
| `display_name` | text | Normalized public display name |
| `facility_type` | enum/text | `school`, `health_facility`, future categories |
| `facility_subtype` | text nullable | Source/normalized subtype |
| `ownership` | enum/text nullable | `government`, `private`, `unknown` |
| `record_status` | enum | `active_in_registry`, `inactive_in_registry`, `unknown`, `under_review`, `merged`—not equivalent to operational status. `merged` is an internal tombstone after a reviewed identity merge |
| `created_at` | timestamptz | First created in PhilFacilities |
| `updated_at` | timestamptz | Last canonical update |

Do not store `is_operational=true` by default. Operational status is separate, source-specific, and only exposed when a credible source actually provides it.

### `source.agencies`

`id`, `name`, `short_code`, `official_domain`, `publisher_type`, `created_at`.

### `source.datasets`

`id`, `agency_id`, `name`, `description`, `source_url`, `access_method`, `terms_url`, `license_identifier`, `redistribution_status`, `update_pattern`, `schema_version`, `is_public_source`, `created_at`.

Use the canonical `redistribution_status` values from `apps/api/philfacilities_api/rights.py`: `unknown`, `review_required`, `approved_public_redistribution`, `approved_with_attribution`, `publicly_available_verified`, `restricted_non_redistributable`, `denied`, and `expired`. The first three public-compatible states are `approved_public_redistribution`, `approved_with_attribution`, and `publicly_available_verified`; publication still requires an approved or published release gate. `publicly_available_verified` means the exact release is verified and publicly available, no explicit prohibition was found, only reviewed institutional fields are published, and provenance, attribution, and a takedown route are recorded. See `docs/14-DATA-INCLUSION-AND-PUBLICATION-POLICY.md`.

### `source.releases`

`id`, `dataset_id`, `source_release_label`, `source_published_at`, `reference_period_start`, `reference_period_end`, `retrieved_at`, `raw_object_uri`, `sha256`, `file_format`, `file_size_bytes`, `row_count_reported`, `row_count_parsed`, `ingestion_status`, `terms_review_status`, `notes`.

### `source.records`

`id`, `release_id`, `source_record_key`, `row_number_or_page`, `raw_payload_jsonb`, `raw_record_hash`, `parsed_at`, `validation_status`.

Retain raw values and source row/page pointers. Avoid copying an entire large source file into PostgreSQL if the object store already preserves it; the parsed row JSON is a queryable record-level representation.

### `source.facility_source_links`

`id`, `facility_id`, `source_record_id`, `source_entity_id`, `match_method`, `match_confidence`, `match_status`, `evidence_jsonb`, `valid_from`, `valid_to`, `reviewed_by`, `reviewed_at`.

`match_status`: `automatic_high_confidence`, `human_confirmed`, `candidate`, `rejected`, `unresolved`.

### `quality.match_candidates`

| Column | Type | Notes |
|---|---|---|
| `id` | uuid | Candidate identifier |
| `candidate_key` | text unique | SHA-256 of algorithm version + source record + proposed facility; prevents duplicate queue rows |
| `source_record_id` | uuid FK | Source record being evaluated |
| `source_facility_id` | uuid FK nullable | Facility currently holding the source record |
| `candidate_facility_id` | uuid FK nullable | Proposed surviving facility |
| `source_agency_code`, `candidate_agency_code` | text nullable | Agencies on each side of the proposal |
| `match_method` | text | Deterministic matcher name, e.g. `exact_normalized_name_psgc_type` |
| `algorithm_version` | text | New versions may generate new candidates for the same pair |
| `match_confidence` | numeric(4,3) | Informational evidence score; never an automatic-merge threshold |
| `match_status` | text | `pending`, `accepted`, `rejected`, `merged` |
| `evidence` | jsonb | Normalized name, PSGC, type, address match, distance, facility snapshots |
| `reviewer`, `reviewed_at`, `review_note` | mixed | Reviewer identity, decision time, and reason. Reviewer details are not exposed publicly |
| `resolution` | jsonb | Merge audit: moved record counts/IDs and facility snapshots. Reviewer identity stays in the internal `reviewer` column and is not included |
| `created_at` | timestamptz | Queue creation time |

Candidates are only proposals. Accepting records the decision; merging is a separate explicit
operation. Rejected rows are retained so the same pair is not re-queued for the same algorithm
version. The public API exposes read-only candidate and resolution data without reviewer name or
review note.

### `geo.geographic_releases`

`id`, `release_label`, `reference_date`, `published_at`, `retrieved_at`, `raw_object_uri`, `sha256`, `source_url`.

### `geo.administrative_units`

`id`, `psgc_code` (text), `name`, `geographic_level`, `parent_psgc_code`, `correspondence_code`, `old_name`, `city_class`, `income_classification`, `urban_rural`, `island_region`, `valid_from`, `valid_to`, `release_id`.

Never assume a PSGC code/name mapping is timeless. Keep release-linked rows and effective periods.

### `core.facility_locations`

`id`, `facility_id`, `source_record_id`, `geom` (geography/geometry point, nullable), `latitude`, `longitude`, `precision`, `method`, `address_text`, `psgc_code`, `valid_from`, `valid_to`, `review_status`.

Precision values: `gps_verified`, `field_verified`, `source_gps`, `map_geocoded`, `barangay_centroid`, `unknown`. Keep source-supplied precision separate from PhilFacilities verification.

## 4. School domain tables

### `school.profiles`

`facility_id`, `deped_school_id`, `sector`, `school_management`, `annex_status`, `offers_es`, `offers_jhs`, `offers_shs`, plus source-record reference and effective dates.

### `school.enrollment_observations`

`id`, `facility_id`, `school_year`, `grade_level`, `sex`, `learner_count`, `source_record_id`, `observed_at`.

A long/fact-table structure is preferred over adding one column for every school year. It supports future years and multiple dimensions.

### `school.resource_observations`

`id`, `facility_id`, `school_year`, `resource_category`, `resource_code`, `value_numeric`, `value_text`, `unit`, `source_record_id`, `observed_at`.

Use a controlled dictionary for resource codes and retain the original source column name/value in the source record.

## 5. Health domain tables

### `health.profiles`

`facility_id`, `doh_facility_id`, `facility_category`, `service_capability_level`, `bed_capacity`, `source_record_id`, `valid_from`, `valid_to`.

### `health.licenses`

`id`, `facility_id`, `issuing_authority`, `license_number`, `license_type`, `source_status`, `valid_from`, `valid_until`, `source_record_id`.

### `health.accreditations`

`id`, `facility_id`, `authority`, `provider_category`, `benefit_package`, `accreditation_category`, `bed_count`, `sector_code`, `source_status`, `valid_from`, `valid_until`, `source_as_of`, `source_record_id`.

Accreditation must be many-to-many and time-bounded. One PhilHealth provider PDF is not a universal facility status.

## 6. Provenance model

For every published attribute, consumers should be able to determine:

- source agency;
- source dataset and release;
- original record identifier;
- original source field/key;
- raw source value;
- normalized value;
- source publication date, if known;
- reference period;
- retrieval and processing timestamp;
- transformation/version identifier;
- review/verification status.

An `attribute_assertions` table or a JSON provenance structure can support field-level attribution. Prefer a relational assertion table for fields used in matching, quality, or user-facing claims.

## 7. History strategy

Use append-only source releases and source records. Never overwrite the raw file. Canonical current-state projections can be updated, but every material change should create a `history.facility_change_events` record with old value, new value, source evidence, and changed timestamp.

Distinguish:

- `source_published_at`: when the agency published the file;
- `reference_period`: the period the data describes;
- `retrieved_at`: when PhilFacilities downloaded it;
- `processed_at`: when ETL completed;
- `valid_from` / `valid_to`: source-reported or inferred effective interval (mark inferred dates as such).

## 8. Data quality model

Quality must be per attribute and source, not one opaque facility score.

Recommended indicators:

- `identity_confidence`;
- `geography_match_status`;
- `coordinate_precision`;
- `coordinate_validation_status`;
- `source_age_days` (calculated at query time or materialized);
- `required_field_completeness`;
- `duplicate_candidate_count`;
- `conflicting_source_values`;
- `terms_publication_status`.

Do not create a single overall trust score until a documented methodology is validated. Display understandable labels and warnings instead.

## 9. Identity resolution rules

Preferred order:

1. Exact, source-specific stable ID within the same agency/source system.
2. Explicit official crosswalk or shared identifier.
3. Exact normalized name + same PSGC unit + compatible facility subtype, with address evidence.
4. Similar name + locality + address/phone evidence produces a candidate only.
5. Conflicting IDs or distant coordinates require human review.

Never auto-merge solely on name similarity. Store rejected and unresolved candidates so the same ambiguous pair is not repeatedly reprocessed.

The implemented queue is `quality.match_candidates`. A candidate moves `pending` → `accepted` or
`rejected` by a named reviewer. `accepted` → `merged` is a second explicit operation that moves
source links, locations, observations, profiles, licences, accreditations, assertions, and issues to
the surviving facility; the retired facility stays as an internal `merged` tombstone. Change events
`facility_merged_into` and `facility_merged_from` preserve the audit trail.

## 10. Retention and deletion

- Retain source releases only as permitted by source terms, agreements, and the inclusion/publication policy.
- If raw file retention is restricted, store only allowed metadata/checksum and document that the source must be reacquired.
- Support source takedown and correction workflows, including the process in `docs/14-DATA-INCLUSION-AND-PUBLICATION-POLICY.md`.
- Retain audit trail for deletions where legally appropriate without retaining prohibited personal information.
